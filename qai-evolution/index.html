Build dossier · MDLC kernel

QAI // ΞVOLUTION

QAI is a quantum circuit SDK and platform: the qai Python SDK (statevector simulation, compilation, Grover and QAOA, validation against a Qiskit reference) plus a multi-tenant web platform that runs simulation, algorithm, validation, benchmark and evolution jobs, keeps hash-verified evidence and gates releases on it. The Evolution Engine is part of QAI: it proposes new QAOA configurations for MaxCut, scores each one on the server, and adopts a candidate only when it is valid and improves the objective by at least a set margin. Every result is noiseless state-vector simulation; no quantum hardware is involved. This page records what the build produced, what passed, what failed on the way, and what is still open.

Shipped · v0.8.0

The Evolution Engine at quantum.mdlc.ai is a demo copy of the QAI web app. It runs the same Next.js frontend on a Cloudflare Worker, but every request is answered from a frozen, invented dataset (a fictional lab), not from the QAI API, database or worker. Browsing works fully. Starting an evolution run or a job computes nothing: it replays a recorded run. Other changes are refused with a read-only error, and nothing is saved. The results on this page come from the real build: its tests, gates and reports, run against the full local stack.

Where evolution fits

The Evolution Engine is not a separate product. It is a thread of features inside the QAI build.

FeatureWhat it added
F-7SDK evolution engine: seeded perturbation of a QAOA configuration; V (every seed's run passes validation) and J (mean of 1 minus the approximation ratio) computed by the engine; a candidate is accepted only when V holds and J ≤ J(Ψn) − ε.
F-14Optimization screens (/app/optimization, the page the demo link opens): create a run, decision timeline, checkpoint history and the current Ψn. The server re-verifies every outcome against the SDK (compliance row S14).
F-26The Evolution Engine section on the landing page (the loop, why it matters, its limits) and a "Load example" on Optimization.
F-31 to F-34Release 0.8.0, the evidence protocol: a governance gate with evidence completeness, a six-test protocol (baseline, improvement, repeatability, generalization on locked splits, governance injections, report), a protocol job and its screen.
F-38 to F-45Validation Lab (R8, R9, unreleased): release decisions with a reason, a versioned active Ψ with promote and rollback, an audit hash chain, an independent MaxCut scorer, classical baselines and ablations with Holm-corrected statistics, and a report bundle labelled "Noiseless state-vector simulation".

Open items

  • HSTS is off on the localhost edge by design, because the stack uses a local certificate (ADR-29).
  • Mobile Lighthouse performance is below 80 on landing and app (63 to 70, LCP 2.7 to 3.6 s) in three full runs, while an isolated measure scored 83. Accepted as host-bound (ADR-56), to be reviewed on the next quiet-host or CI run.
  • Not a public deploy: the stack is local. A remote host needs a public certificate, HSTS enabled, real secrets, a Valkey password and database backups.
  • The 50k-concurrent scale target is not demonstrated (single host; ADR-09), and /api/health p95 missed its 500 ms target on the Docker Desktop host.
  • Carried low and info review items: N-R33-3, N-R33-5, N-R32-1, N-R32-2, N-R28-3, N-R28-4, N-R29-2 to N-R29-5, N-R30-5 and N-R30-6, plus the accepted security residuals above.
  • R7 to R9 are not yet a numbered release; the last release is 0.8.0. COMPLIANCE.md (36 rows: 16 implemented, 20 with a residual or waiting on measurement, 0 gaps) was last re-checked at re-entry R3.
  • All results are noiseless state-vector simulation on small instances (the protocol uses 6 to 10 nodes). No noisy simulator or hardware backend exists.
