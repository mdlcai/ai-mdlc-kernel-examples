### THE PROBLEM

The global payments ecosystem is fragmented, expensive, operationally complex, and heavily dependent on disconnected financial infrastructure.

Businesses, developers, and financial institutions must navigate multiple payment processors, banking networks, card brands, digital currencies, and financial service providers, each operating through proprietary APIs, incompatible data structures, different settlement processes, and independent security requirements.

As organizations expand across markets, currencies, and payment methods, this fragmentation creates significant technological, financial, and operational challenges.

### CRITICAL INDUSTRY CHALLENGES

**1. Fragmented Payment Infrastructure**

Organizations must maintain separate integrations with payment processors such as Stripe, Fiserv, and Worldpay. Each provider introduces different APIs, transaction models, reporting formats, and operational requirements, increasing development costs and limiting interoperability.

**2. Processor Dependency and Vendor Lock-In**

Businesses frequently become dependent on a single processor, limiting negotiating power, operational flexibility, geographic expansion, and their ability to respond to outages or changing commercial terms.

**3. Inefficient Transaction Routing**

Traditional payment integrations often lack the intelligence to dynamically select processors based on transaction costs, authorization rates, geographic availability, currency, network performance, and fraud risk.

Consequently, merchants may experience unnecessary processing expenses, avoidable declines, and reduced payment performance.

**4. Fragmented Financial Visibility**

Transaction data, processing fees, settlements, refunds, disputes, and reconciliation records are distributed across multiple systems.

Financial teams lack a unified, real-time view of money movement, creating manual processes, reporting inconsistencies, and operational inefficiencies.

**5. Increasing Fraud and Security Threats**

Payment fraud, account takeover, transaction abuse, credential compromise, and evolving cyber threats require increasingly sophisticated detection and prevention capabilities.

Disconnected fraud systems create inconsistent risk assessments and limit the ability to correlate suspicious activity across processors and payment channels.

**6. Complex Compliance Requirements**

PCI DSS, card network requirements, ACH operating rules, privacy regulations, and jurisdiction-specific financial regulations introduce significant compliance obligations.

Organizations must maintain security and governance across multiple providers while protecting sensitive financial information and maintaining auditable transaction records.

**7. Limited Resilience and Processor Failover**

Processor outages, degraded network performance, API failures, and service disruptions can interrupt payment acceptance and directly affect revenue.

Many existing integrations lack reliable cross-processor failover, transaction state synchronization, and safeguards against duplicate financial transactions.

**8. Disconnected Traditional and Digital Payments**

Card networks, ACH, bank transfers, Bitcoin, Lightning, and emerging digital asset payment systems operate through different technological and regulatory frameworks.

Integrating these payment methods into a consistent merchant experience requires specialized infrastructure and significant engineering effort.

**9. Limited Intelligent Automation**

Traditional payment platforms frequently rely on static configurations, fragmented analytics, and manual operational decisions.

They lack unified intelligence capable of continuously evaluating processor performance, identifying financial anomalies, recommending routing improvements, and supporting proactive operational decisions.

### 1. MERCHANT ONBOARDING & TENANT PROVISIONING

**Objective:** Enable businesses and SaaS platforms to onboard merchants, configure financial services, and activate supported payment processors through one centralized workflow.

**Workflow:**

1. Merchant registers through the RΛILS dashboard or API.
2. Platform creates an isolated merchant tenant.
3. Merchant submits business information and required verification documentation.
4. Identity, business verification, and applicable KYC/KYB checks are performed through authorized providers.
5. Merchant connects existing processor accounts or initiates supported processor onboarding.
6. RΛILS validates processor credentials and available capabilities.
7. Payment methods, currencies, routing policies, and security settings are configured.
8. Merchant receives API credentials, sandbox access, and dashboard permissions.
9. Production processing is enabled following required verification and approval.

**Expected outcome:** Faster onboarding, consistent merchant configuration, and secure multi-tenant provisioning.

### 2. UNIFIED PAYMENT PROCESSING

**Objective:** Process payments across supported providers through a consistent developer API.

**Workflow:**

1. Merchant application creates a payment intent.
2. RΛILS authenticates the request and validates tenant permissions.
3. Platform verifies transaction amount, currency, payment method, and idempotency key.
4. Payment method credentials or processor tokens are securely resolved.
5. Transaction enters the payment orchestration engine.
6. Routing engine selects an eligible processor.
7. Processor adapter translates the request into provider-specific instructions.
8. Authorization response is normalized into the RΛILS transaction model.
9. Payment state is persisted and corresponding financial events are recorded.
10. Merchant receives an API response and subsequent lifecycle webhooks.

**Supported lifecycle operations:**

- Payment intent creation
- Authorization
- Capture
- Partial capture where supported
- Void and cancellation
- Full and partial refunds
- Payment status retrieval
- Dispute and chargeback tracking

**Expected outcome:** One consistent payment interface across multiple processors.

### 3. INTELLIGENT MULTI-PROCESSOR ROUTING

**Objective:** Select the most appropriate payment processor for each eligible transaction.

**Workflow:**

1. RΛILS receives a validated payment request.
2. Routing engine identifies compatible processors.
3. Platform evaluates merchant-specific routing policies.
4. Available processors are assessed using relevant signals.
5. Engine calculates a routing decision.
6. Risk and compliance restrictions are enforced.
7. Selected processor receives the authorization request.
8. Transaction outcome and processor performance are recorded.
9. Routing analytics update future recommendations.
10. Authorized policy changes may improve subsequent routing decisions.

**Routing decision factors:**

- Processing fees and effective transaction cost
- Historical authorization performance
- Processor availability and response latency
- Merchant location and acquiring geography
- Currency and payment method compatibility
- Transaction risk
- Card brand and network requirements
- Merchant contractual preferences
- Processor capacity and restrictions

**Expected outcome:** Reduced avoidable processing costs, improved authorization performance, and greater processor flexibility.

### 4. PROCESSOR FAILOVER & PAYMENT RESILIENCE

**Objective:** Maintain payment availability during processor failures without compromising transaction integrity.

**Workflow:**

1. RΛILS continuously monitors processor health.
2. A processor experiences an outage, timeout, or degraded service.
3. Health monitoring identifies the condition.
4. Circuit breakers prevent unnecessary requests to unhealthy services.
5. RΛILS determines whether the original transaction completed.
6. Transactions with uncertain outcomes enter a verification or recovery state.
7. Eligible transactions may be routed to an alternate processor when safe.
8. Transaction identifiers and idempotency protections prevent duplicate processing.
9. Merchant receives updated payment status.
10. Recovery events are recorded for operational review.

**Critical requirement:** An ambiguous authorization response must never trigger an uncontrolled cross-processor retry.

**Expected outcome:** Higher operational resilience with controlled financial risk.

## Design Template

An HTML design template was uploaded with this project (built by the customer
in Claude Design / artifacts). Fetch it at build time via the
`get_design_template` MCP tool — that is the source of truth, not this section.

### How to use it
- **Copy the template's `:root` design tokens verbatim FIRST.** The template
  declares its palette, typography, spacing scale, radius, and shadow as CSS
  custom properties on `:root` (`--color-*`, `--font-*`, `--space-*`,
  `--radius-*`, `--shadow-*`). Transcribe those values EXACTLY into the
  project's token layer (CSS variables / Tailwind theme / equivalent) — do not
  re-interpret, round, average, or "improve" them. This copied set is the
  canonical design-token system for the whole build.
- If the build needs a token the template did not declare (e.g. a missing
  state color or extra elevation), derive it to sit alongside the copied
  palette — never replace a value the template set.
- Use the markup as the visual scaffold for the landing/home surface — port
  its sections, hero, nav, and components into the project's framework rather
  than reinventing the layout.
- The copied tokens are binding for the ENTIRE build, OVERRIDING the values in
  `get_project_config` / the Design Language section below wherever they
  conflict. Express archetype-driven screens (anything not in the template)
  through these same tokens so the whole app stays visually coherent.
- Save the raw template to the project root as `DESIGN-TEMPLATE.html`, and
  record in `DECISIONS.md` the exact `:root` block you copied.

### If the template carries no `:root` block
- Some Claude Design exports style every element inline instead of declaring
  CSS custom properties. The template is still binding: derive the token set
  FROM the markup — background/surface/text/accent colours from the inline
  `style` attributes (ranked by frequency and role), the `font-family` stack
  from its `@font-face` + inline declarations, and radius/spacing/shadow from
  the values the template actually uses. Write that derived set as the
  project `:root` block, use it exactly as you would a copied one, and record
  it in `DECISIONS.md` with a note that it was derived rather than copied.
- `{{placeholder}}` tokens, `<sc-for>` loops and `<script type="text/x-dc"
  data-props="…">` tags are Claude Design component scaffolding. Treat each
  `data-props` default as the chosen value, treat `<sc-for>` bodies as the
  item template for a data-bound list, and never render a placeholder
  literally.
- If the file begins with a loader shell (`<noscript>This page requires
  JavaScript</noscript>` plus `<script type="__bundler/template">`), the real
  page is the JSON string inside that script and the assets are the base64
  entries in `__bundler/manifest`; decode those before reading tokens.
