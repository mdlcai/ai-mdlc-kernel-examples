CyberOps Platform Architecture

A unified, multi-tenant, AI-assisted security-operations platform. It turns asset discovery, vulnerability scanning, AI-assisted penetration testing, OSINT/threat analysis, and compliance mapping into a single correlated view of organizational risk — with continuous retesting, across an organization's authorized attack surface.

Build depth comprehensive Scale tier large · 50k+ concurrent Monorepo npm workspaces API NestJS 11 · REST /v1 Web Next.js · App Router DB PostgreSQL 18 · RLS

§1 System Overview

Core problem → solution: fragmented security tooling → one workflow that discovers, assesses, validates, correlates, prioritizes, and retests.

Five key workflows (SPEC §5)

W1 · AI Pentest

AI-powered automated penetration test — multi-agent planner produces attack paths + evidence.

W2 · Discovery & VA

Asset discovery & vulnerability assessment across the authorized surface.

W3 · OSINT

Threat & OSINT investigation — correlate indicators against assets and findings.

W4 · Compliance

Compliance & security-posture assessment mapped to control frameworks.

W5 · Retest

Finding remediation & continuous retesting with a tamper-evident trail.

⚠ Safety boundary (binding, RESEARCH §5)

The platform runs authorized offensive tooling only. It ships real safe recon (DNS / HTTP-fingerprint / TLS) and a template-driven finding engine, and models exploit-validation as state — unvalidated → validating → validated | failed — gated behind verified authorization scope + human approval. It does not ship a live-exploitation module that fires payloads at arbitrary targets. Enforced by the authorization-scope, SSRF, rate/concurrency, and agent-sandbox invariants (§9).

§4 Data Layer

PostgreSQL 18 · TypeORM

  • PKs = uuidv7() — timestamp-ordered, index-friendly at insert scale.
  • Finding payloads / evidence = jsonb; enums as Postgres enum.
  • Reversible DataSource migrations (up/down); seed for roles, severities, frameworks, demo org.

Tenant isolation (defense in depth)

  • Every tenant-owned table carries tenant_id.
  • Postgres RLS scopes by a session app.tenant_id GUC set per request/job.
  • TenantScopedRepository is the single chokepoint that sets the GUC and filters.
  • Object-level assertResourceAccess on every user-owned resource and its sub-resources.

Idempotency & audit chain

  • inbound_webhook_events UNIQUE (provider, event_id).
  • pending_emails UNIQUE (to_address, template_key, business_ref_id).
  • Audit: hash = sha256(prev_hash || canonical_json(payload)) — append-only, no update/delete path.

Pooling & scale

  • pg pool tuned; PgBouncer (transaction mode) documented for prod.
  • Hot tables findings, scan_results indexed on (tenant_id, severity, created_at).
  • Read-replica split documented as a cloud-scale step.

§5 Scanner & Adapter Engine

ScanOrchestrator (BullMQ worker) selects adapters by profile → streams RawFindings → normalizes to Finding (CVSS/CWE/severity) → persists → emits WS progress.

Built-in safe adapters always available

  • DnsReconAdapter — records + bounded subdomain wordlist (authorized zones only).
  • HttpFingerprintAdapter — headers, tech/version, missing security headers, cookie flags, safe .git/.env probes.
  • TlsInspectAdapter — cert chain, expiry, weak protocol/cipher.
  • TemplateEngineAdapter — Nuclei-style YAML signatures (offline corpus) → CVE/CWE-tagged findings.

External adapters degrade gracefully

  • NucleiAdapter — spawns nuclei -jsonl, parses JSONL to findings.
  • TrivyAdapter — spawns trivy … --format json for repo/IaC/SBOM findings.

Used only when the binary is present; the platform stays fully functional on the built-in safe set alone.

◆ ScannerAdapter interface

{ id, kind, capabilities, isAvailable(): Promise<boolean>, run(target, opts, ctx): AsyncIterable<RawFinding> } — pluggable, testable, safe-by-construction.

§6 AI Pentest Orchestration (multi-agent)

PentestPlanner decomposes a run into phases following the VulnBot/AutoPentest/xOffense multi-agent pattern. Each phase is an agent role with an allowlisted tool set that calls only the safe scanner adapters.

LLM provider & prompt-injection

  • LlmProvider interface — provider-abstracted; Claude Messages API default.
  • All target-derived text (banners, HTTP bodies, OSINT) is untrusted — passed as data, never as instructions (mitigation R7).

Offline / degraded mode

  • With no LLM key, the planner falls back to a deterministic rule-based phase engine.
  • A pentest run stays demonstrably functional without external AI — findings + attack paths from the safe adapters.
  • Output: AttackPath (MITRE ATT&CK + CWE), Evidence (encrypted at rest), risk-scored Findings.

§7 Realtime, Async, Notifications & Observability

WebSocket

Socket.io gateway + @socket.io/redis-adapter for multi-instance fan-out. Auth: JWT on connection, Origin allowlist, per-connection message-rate budget, channel authorization (a client may only join rooms for its own tenant's scans).

Queues

BullMQ v5 on Redis (maxmemory-policy=noeviction, dedicated logical DB). Queues: scan outbox email webhook pentest. Idempotent jobs; DLQ after capped backoff.

Outbox relay

Drains outbox_events → search index (Postgres FTS in-cluster; Algolia/OpenSearch documented swap), email, outbound webhooks (HMAC signed at insert, Idempotency-Key per send, ≤5 attempts).

Email & telemetry

Resend v6 via the email queue with rate limiting — never inline in a request handler. Sentry v10 (instrument.ts first), structured JSON logs (pino), Prometheus-style /metrics + /api/health.

◆ Build-environment version note (ADR-006)

RESEARCH verified the bleeding edge (Next 16 / Tailwind v4 / TypeORM 1.1). Where a bleeding-edge major introduced install/build instability in the sandbox, the build pins the nearest battle-tested major (Next 15, Tailwind v3, TypeORM 0.3) and logs the substitution as an ADR — the deliverable (stack, design system, workflows) is preserved; only the pin moves. A build-environment substitution, not a stack change.

§12 Threat Model

Five trust boundaries, each with its own controls; top risks R1–R8 each map to an invariant and a mitigation.

1 · Browser ↔ API

JWT cookie · CSRF/Origin guard · Zod validation.

2 · API ↔ Postgres

RLS · parameterized queries · least-privilege role.

3 · Worker ↔ target network

SSRF guard · authorization scope · isolated egress.

4 · API ↔ LLM / target text

Untrusted-data handling · prompt-injection mitigation.

5 · API ↔ third-party webhooks

HMAC verify-before-DB. Top risks R1–R8 — authorization scope, SSRF, secret handling, cross-tenant leakage, audit tampering, scan-proxy abuse, prompt injection, artifact handling — each map to an invariant (§9) and a mitigation (§5).
