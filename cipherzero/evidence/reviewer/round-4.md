## Focus items

**C-3 (d9793fb, GD-0058): ops job_runs (tenant_id, id) index and two-scope merge — PASS.**
- `pageOf` runs one equality query per scope, `tenantId = t AND job? AND id < cursor ORDER BY id DESC LIMIT take` with `take = limit + 1` (ops.ts:144-149, packages/core/src/db/pagination.ts:10-14). The `(tenant_id, id)` index serves it in order (migration 20261110000000; schema.prisma:552).
- The top n of each scope is enough. Any row in the overall top n (by id desc, under the same `id < cursor` predicate) is in the top n of its own scope, so `[...own, ...global]` sorted desc and sliced to `take` is exactly the old `IN` query's result (ops.ts:165).
- Ties cannot occur: `id` is the primary key, unique across both scopes, so the order is total and no row is dropped or repeated at a page edge.
- The JS comparator sorts lowercase canonical UUIDv7 text, and the Postgres text order of the same strings gives the same result (the hyphens sit at fixed positions, and 0-9 come before a-f in both).
- Cursor semantics are unchanged. `toPage` keeps `limit` rows and encodes the last id (pagination.ts:17-22). The next request applies `id < cursor` to both scopes, so pages stay contiguous.
- `q.job` is applied to both scopes, and global rows stay redacted by `jobRunDto`.
- Gap (scored in item 2): no test spans more than one page or interleaves tenant and global ids.

**C-4 (802a5bc, GD-0059): last run per job via findFirst probes — FAIL (item 6).**
- The probes are correctly scoped, two per job (tenant and `*`, ops.ts:153-157). Each is served by the `(job, tenant_id, window_start)` unique index. Across scopes, the newest by `startedAt` wins (ascending sort, then last write into the Map, :162-166).
- Within one scope, though, the probe picks the newest window, not the newest start, so the "last run" is wrong in the manual-before-cron and retry cases above.
- The only lastRun assertion (apps/api/test/ops.test.ts:112) seeds a single run per job, so it cannot tell the two orderings apart.
