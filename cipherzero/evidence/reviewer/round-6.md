## FAIL items (actionable)

### FAIL-1 (F-6): a `policy_activate` approval cannot be retried after a partial failure; the activation can be left unaudited
- **Where:** apps/api/src/services/policies.ts:430 (`if (b.status !== 'pending_approval') throw problems.invalidTransition(...)`), together with :440-462. trust-core commits the active/superseded flip in its own transaction (apps/trust-core/src/service.ts:536-551). The API then writes `approverId` and the `policy.activate` audit in a separate transaction afterwards.
- **Failure scenario:**
  1. The approver approves. `deps.trust.activateBundle` succeeds, so the bundle is now `active` and the previous bundle is `superseded`.
  2. The API transaction at :446-462 then fails: a Postgres blip, a serialisation or timeout error, or a process crash.
  3. services/approvals.ts:166-185 records `result.error` and `approval.execute_failed`, and the approval stays `approved`.
  4. The approver retries, as approvals.ts:140-141 allows. The executor re-reads the bundle, finds `active`, and throws 409 INVALID_TRANSITION at :430.
  5. The retry fails every time. The approval can never reach `executed`, `policy_bundles.approver_id` stays null, and the evidence chain has no `policy.activate` event for a bundle that is enforcing.
- **Why it matters:** this breaks the stated executor contract (services/approvals.ts:17-18: "executors are idempotent, so an approval whose execution failed stays `approved` and the same approver can retry it"). Activating a bundle is a two-person, audited action (ADR-057), and an enforcing bundle with no activation record weakens INV-13's evidence guarantee. The sibling executors handle the same situation: `keyDestroyExecutor` (services/keys.ts:390-431) and `apexRemediationExecutor` (services/apex.ts:541-549) both return early when already done.
- **Fix:**
  1. Make the executor resumable. If `b.status === 'active'` and `b.activatedAt` is set, and the bundle's digest equals `payload.digest`, skip the trust call. Otherwise call trust-core as now.
  2. In both cases, write `approverId` and the `policy.activate` audit. Guard that write so it happens only once, for example with `updateMany where { id, tenantId, approverId: null }` and appending the audit only when count = 1. Return the same result shape.
  3. Add an integration test: stub the post-trust transaction to fail once, then show that the approver's retry reaches `executed` and leaves exactly one `policy.activate` event.
