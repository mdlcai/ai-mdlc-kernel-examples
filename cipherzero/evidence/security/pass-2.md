## New findings in the diff

### SEC-8 — MEDIUM — Credential-bearing form without `method="post"` (new MFA re-auth form)
- Clause violated: BUILD.md §Security Audit Gate, web delivery category ("a credential-bearing form without `method="post"` … degrades to a GET that writes the password into the URL, the access log and history when hydration fails"); SPEC §4 credential handling. Pass 1 recorded every credential form as `method="post"`; this form is new in 32b23e1.
- Location: `apps/web/src/app/(console)/settings/settings-client.tsx:254` (`<form className="stack form-narrow" onSubmit={(e) => void begin(e)} noValidate>`), which contains `<Input name="currentPassword" type="password">` at :256.
- Exploit path: For any user without TOTP, the form is server-rendered on the initial `/settings` load (`!user.mfaEnabled && !setup`). The user may type their password and press Enter before hydration (slow network, a blocked or failed chunk, a CSP chunk block, or a JS error). The browser then performs a native GET to `/settings?currentPassword=<password>`. The plaintext password lands in the URL bar, browser history and synced history, and in any server or proxy request log that records query strings. By definition this user has no second factor, so the leaked password alone takes over the account.
- Remediation: Add `method="post"` to the form at settings-client.tsx:254, matching the password-change form at :137. Optionally add `method="post"` to the TOTP code form at :223 for consistency. Add a lint or e2e assertion that every form containing `type="password"` has `method="post"`.

### SEC-9 — MEDIUM — Quantum migration moves data off keys named in key-scoped policy rules, which silently stops applying those rules
- Clause violated: ARCHITECTURE §5.3 (PDP; key-scoped `resources.keyIds` rules) and §9 policy-change invariants (policy changes take effect only through a signed, approved `policy_activate`, with separation of duties); SPEC §4 least privilege.
- Location: `apps/api/src/services/quantum.ts:470-484` (`migrateAssets` calls `moveObjectsToKey(deps, u, requestId, key.id, successor.id)` and then `retireSource`) and `apps/api/src/services/vault.ts:430-498` (`moveObjectsToKey`). Neither checks whether the active policy bundle (or active grants) mentions `fromKeyId`. The trust-core PDP evaluates `resource.keyId` (apps/trust-core/src/service.ts:262; packages/core/src/policy/index.ts:84-86). The default bundle allows every workload and agent, and every staff role, to use every key (`allow-workload-crypto` and `allow-staff-crypto`, policy/index.ts:170-179). Tenants therefore restrict a sensitive key with a `deny` rule scoped to `resources.keyIds: [<key A>]`.
- Exploit path: A tenant has an approved (two-person, signed) rule `deny key.decrypt for workload X on keyIds [A]`. A single owner, admin or security_officer creates a quantum plan that includes key A's asset and advances it to `migrating` (`POST /v1/quantum/plans/:id/advance`). That call needs only the WRITER role, with no approval and no step-up. Every vault object on A is decrypted and re-sealed under the new key `A-pq`, and A is disabled. The deny rule still names A, so it no longer matches. Workload X, or any principal the rule excluded, now decrypts those objects through `allow-workload-crypto`, supplying the object's purpose, which the caller controls (SEC-4). One writer has bypassed a key restriction that took a dual-approved policy change to establish. The same thing happens by accident when an operator follows W5 in good faith. Allow-lists scoped to A (and grants with `keyIds: [A]`) fail closed instead, which is an availability problem rather than a confidentiality one.
- Remediation: Before `moveObjectsToKey` in `migrateAssets`, load the tenant's active policy bundle and the active grants. If any rule's `resources.keyIds` (or any active grant's `keyIds`) contains `key.id` but not `successor.id`, do not move. Emit `action: 'operator_action_required'` with a detail like `"Policy rule <id> references key <A>; add <A-pq> to it (policy_activate approval) before migrating."`, so the step stays incomplete and the plan cannot reach `validated`. Add an integration test: a deny rule scoped to key A, then advance the plan, then assert that the objects stay on A and the step is `operator_action_required`.

### SEC-10 — LOW — Re-authentication checks are throttled per IP only, with no account lockout
- Clause violated: SPEC §4 brute-force protection; ASVS V2.2.1.
- Location: `apps/api/src/services/auth.ts:355-356` (`mfaSetup`, new in the batch) and the earlier identical pattern at :418-419 (`changePassword`). `loginLimiter` keys on `login:${ip}:${emailHash}` (auth.ts:42-45), and a failure here never increments `failedLogins`/`lockedUntil`, unlike `login` (auth.ts:286-298).
- Exploit path: An attacker holding a stolen session cookie can spread password guesses for `/auth/mfa/setup` across many source IPs. Each IP gets its own bucket and the account never locks, so the attacker can guess the password offline from the 422 responses, then enroll their own authenticator (SEC-3's threat). This is bounded by argon2 cost, the 30-minute idle and 12-hour absolute session lifetime, and the 15-character minimum password.
- Remediation: Add a per-user bucket (`reauth:${userId}`) alongside the per-IP bucket in `mfaSetup` and `changePassword`, or count failures toward `failedLogins` / `lockedUntil` the way `login` does.
