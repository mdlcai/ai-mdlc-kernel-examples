## Product Vision
**Problem:** Modern digital infrastructure operates on fragmented trust.
Organizations depend on disconnected identity providers, encryption services, key management systems, secrets vaults, access policies, and security monitoring platforms to protect their most sensitive assets. These systems often operate independently, creating security gaps, inconsistent enforcement, limited visibility, and complex operational dependencies.
Traditional security architectures assume that authentication establishes trust, encryption guarantees protection, and compliance demonstrates security. In reality, identities can be compromised, credentials can be abused, cryptographic keys can be exposed, and authorized systems—including autonomous AI agents—can perform actions beyond their intended purpose.
The rapid adoption of AI-driven automation introduces another critical challenge: machines are increasingly making decisions and accessing sensitive systems at speeds that exceed traditional human-centered security controls. Meanwhile, emerging quantum computing threats are forcing organizations to reassess cryptographic dependencies and prepare for long-term algorithm migration.
Existing solutions address individual components of these problems but rarely provide a unified mechanism to continuously verify identity, enforce cryptographic authorization, govern key lifecycles, evaluate risk, and produce verifiable security evidence.
Organizations need more than another encryption product, identity provider, or secrets manager.
They need a sovereign cryptographic trust infrastructure capable of protecting human identities, machine workloads, AI agents, applications, and sensitive data under one continuously governed security model.
The fundamental challenges
- Fragmented trust: Identity, encryption, authorization, and cryptographic governance exist across disconnected systems.
- Loss of cryptographic sovereignty: Organizations may depend on external providers for critical key management and security operations.
- Static authorization: Traditional access policies struggle to account for changing identity, workload, and risk conditions.
- Autonomous AI exposure: AI agents introduce new risks involving excessive privileges, credential misuse, and ungoverned machine-to-machine access.
- Cryptographic uncertainty: Legacy algorithms, incomplete inventories, and evolving quantum threats complicate long-term data protection.
- Limited assurance: Security teams often cannot continuously demonstrate that cryptographic operations were authorized, correctly enforced, and independently verifiable.
- Operational complexity: Multiple security products increase integration overhead, configuration drift, incident response time, and compliance costs.
The opportunity
CIPHΞRZER0 addresses these challenges by establishing a unified cryptographic trust plane where identity, authorization, encryption, key sovereignty, adaptive intelligence, and governance operate together.
Rather than treating trust as a permanent state granted after authentication, CIPHΞRZER0 treats trust as a continuously evaluated and cryptographically enforced decision.
Its architecture combines deterministic security controls with AI-assisted analysis, allowing organizations to identify emerging risks, recommend corrective actions, and validate security improvements without surrendering control of critical cryptographic operations.
Core principle

08 // Security architecture
The security model should be stricter than a conventional multi-tenant SaaS.
Required controls
- Tenant-scoped cryptographic authorization with deny-by-default policy.
- Mutual TLS and workload identity for service-to-service communication.
- Strong administrator authentication and separation of duties.
- Non-exportable keys where supported by HSM/KMS.
- Authenticated encryption with enforced nonce uniqueness.
- Strict isolation of cryptographic workloads from AI inference.
- Tamper-evident, externally anchorable audit evidence.
- Explicit authorization for every sensitive key operation.
- Signed, versioned policy bundles.
- Secure bootstrap, backup, recovery, and emergency revocation.
- Secure software supply chain, signed releases, and reproducible deployment evidence.
- Rate limits, quotas, abuse detection, and tenant resource isolation.
- Defined fail-closed behavior for authorization uncertainty, with carefully bounded offline capabilities.
Compliance alignment
Design for control mapping and evidence generation against NIST CSF 2.0, NIST SP 800-53, NIST SP 800-57, relevant NIST post-quantum standards, ISO 27001, SOC 2, and PCI DSS where applicable.
Alignment does not mean certification. FIPS-validated cryptographic modules, PCI applicability, and formal attestations require separate validation.

### How to use it

  custom properties on `:root` (`--color-*`, `--font-*`, `--space-*`,

- If the build needs a token the template did not declare (e.g. a missing

  palette — never replace a value the template set.
- Use the markup as the visual scaffold for the landing/home surface — port
  its sections, hero, nav, and components into the project's framework rather
  than reinventing the layout.
- The copied tokens are binding for the ENTIRE build, OVERRIDING the values in
  `get_project_config` / the Design Language section below wherever they
  conflict. Express archetype-driven screens (anything not in the template)
  through these same tokens so the whole app stays visually coherent.
- Save the raw template to the project root as `DESIGN-TEMPLATE.html`, and
  record in `DECISIONS.md` the exact `:root` block you copied.

### If the template carries no `:root` block
- Some Claude Design exports style every element inline instead of declaring
  CSS custom properties. The template is still binding: derive the token set

  `style` attributes (ranked by frequency and role), the `font-family` stack

### 3.4 Security & compliance research

**Passwords** ([NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html))
- Single-factor passwords need at least **15** characters (§3.1.1.2). That is stricter than the kernel's PCI floor of 12, so 15 is adopted.
- Accept passwords of at least 64 characters.
- No composition rules and no periodic rotation.
- Check the whole password against a blocklist.
- Rate-limit failed attempts (§3.2.2). The limiter runs before the hash compare.

**Breached passwords** ([HIBP API v3](https://haveibeenpwned.com/API/v3))
- Call `GET https://api.pwnedpasswords.com/range/{5 hex SHA-1 prefix}` with `Add-Padding: true`. No API key is needed.
- Sovereign deployments must not require an outbound call, so offline mode falls back to a bundled top-N blocklist.

**Admin strong authentication**
- Admin roles must use TOTP ([RFC 6238](https://www.rfc-editor.org/rfc/rfc6238)) as a second factor.

**Separation of duties**
- A two-person rule applies to activating a policy bundle, destroying a key, and APEX high-risk remediation.
- The requester can never be the approver.

**Webhooks** ([Stripe webhooks](https://docs.stripe.com/webhooks))
- Verify `Stripe-Signature` (`t=`, `v1=`), an HMAC-SHA256 over `"{t}.{rawBody}"`, against the **raw body**.
- Use a constant-time compare and a 300 s tolerance; a tolerance of 0 is not allowed.
- Ignore any scheme other than `v1`.
- Delivery is at-least-once, unordered, and retried for up to 3 days, so dedupe on the event id.
- Return 2xx quickly and process asynchronously in BullMQ.

**Error contract**
- [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html) obsoletes RFC 7807. The `application/problem+json` media type is unchanged and extension members are allowed.
- The extensions `code`, `requestId` and `errors[]` therefore comply. The kernel's "RFC 7807" wording is satisfied by following RFC 9457.

**Key wrapping**
- Classical KEK→DEK wrapping uses AES-256-GCM with AAD binding (`tenant‖key_id‖version`). [RFC 3394](https://www.rfc-editor.org/rfc/rfc3394) AES-KW was considered.
- The hybrid PQC profile is an HPKE-style combiner ([RFC 9180](https://www.rfc-editor.org/rfc/rfc9180)): X25519 and ML-KEM-768 shared secrets feed HKDF-SHA-256, which keys an AES-256-GCM wrap.
- Policy bundles and audit checkpoints carry two signatures, Ed25519 ([RFC 8032](https://www.rfc-editor.org/rfc/rfc8032)) and ML-DSA-65. Both must verify.

**Transport**
- Caddy terminates HTTPS with TLS 1.2 or later, redirects :80 to :443 with a 308, and sends HSTS `max-age=31536000` only when `HSTS_ENABLED=true` behind a trusted public certificate. The local `tls internal` deploy omits HSTS by design (ADR-017).
- Service-to-service traffic (api ↔ trust-core gRPC) uses **mTLS** with a private CA generated at bootstrap. Each workload's SPIFFE ID goes in its certificate's SAN URI.

**At rest**
- PII (emails, display names) and secret payloads use column-level AES-256-GCM under the tenant DEK.
- Lookup identifiers such as email are stored as HMAC-SHA-256 blind indexes.
- Volume encryption is ⚠ delegated to the infrastructure.

### 3.5 Data & integration research

**Tenancy**
- Every row carries `tenantId`. The repository layer requires a tenant context, and reads of another tenant's records return 404.
- Postgres row-level security (RLS) was considered as defence in depth. It is deferred because the Prisma adapter would need a per-request `SET` inside a transaction. This is tracked as a risk.

**Payments (has_payments)**
- Billing is subscription-based. Plans are priced in integer minor units (`amount_minor BIGINT`, `currency CHAR(3)`).
- Checkout intents are created with an `Idempotency-Key` that has a UNIQUE constraint.
- Payment state changes only on a verified webhook: `pending→succeeded→refunded|disputed|charged_back`.
- The Stripe secret is optional. Without it, `BILLING_MODE=simulated` provides a local signed-webhook simulator, which is the Contract Smoke fallback.

**Scheduled work (has_scheduled_work)**
- All jobs run on BullMQ job schedulers in UTC. Each job exposes `runXForOrg(orgId)` as well as an all-tenant sweep.
- Each job claims its rows idempotently: `UPDATE … SET claimed_at=now() WHERE claimed_at IS NULL`.
- Jobs:
  - Key rotation when due (by cryptoperiod or usage).
  - Grant expiry and revocation propagation.
  - Audit checkpoint signing.
  - APEX anomaly scan.
  - Quantum inventory refresh.
  - Retention purge for webhook idempotency rows, which are kept for at least 72 h.

**APEX telemetry**
- APEX reads only real, persisted operation records: `crypto_operations`, `policy_decisions` and `auth_events`.
- No live telemetry is invented. Empty states are shown explicitly.

### 3.7 Operational research

**Compose topology**
- `caddy` (:80/:443) fronts `web` (Next.js standalone) and `api` (the Express REST gateway).
- `api` calls `trust-core` over gRPC with mTLS.
- Other services: `worker` (BullMQ), `postgres` primary and `postgres-replica` (streaming), `redis`, `prometheus` and `grafana`.

**Service behaviour**
- Health: `GET /api/health` returns `{status,version,commit,checks}` within 500 ms. The build identity comes from the `GIT_COMMIT` build-arg.
- Graceful shutdown: on SIGTERM, stop accepting new requests, drain in-flight work, then close the Prisma, Redis and gRPC clients. `tini` runs as PID 1.
- Header limits: Node runs with `--max-http-header-size=32768`. Caddy needs no change, since Go's default header limit is 1 MB.

### 3.8 Performance & scale research

**Latency targets**
- p95 policy evaluation under 25 ms. The bundle is compiled in-process, so there is no network hop.
- p95 key operation under 100 ms. This covers the trust-core gRPC hop plus AES-GCM.

**Large-tier mechanisms**
- A read replica serves list and report queries.
- Redis caches the active policy bundle and the revocation set.
- `/_next/static` is immutable and CDN-ready.
- `api` and `worker` are stateless and can autoscale. BullMQ failed jobs go to a `dead-letter` queue (DLQ).
- Rate limiting happens at the Caddy edge and through per-tenant token buckets in Redis.

**Scale claim**
- 50k concurrent users is an architectural design target. The local single-host deploy is load-tested at ≥1k VUs with k6. The extrapolation to 50k is documented, not claimed as proven.

### 5.1 Threat model (STRIDE over the trust boundaries)

Trust boundaries:
- Browser ↔ Caddy edge.
- Edge ↔ web / api.
- api ↔ trust-core (mTLS).
- api / worker ↔ Postgres / Redis.
- Agent workloads ↔ api (grant tokens).
- External webhook ↔ api.

| STRIDE | Threat | Control |
|---|---|---|
| Spoofing | Forged workload or agent identity | mTLS with a SPIFFE SAN check on gRPC. Agent grants are opaque 256-bit tokens stored as SHA-256 hashes, scope-bound, with a TTL of ≤15 min. |
| Spoofing | Session theft | Cookie set HttpOnly, Secure and SameSite=Strict. The session id rotates. Mutations require a CSRF double-submit token. |
| Tampering | Edits to audit records | Hash chain, signed checkpoints, and a verification job plus UI. |
| Tampering | Ciphertext manipulation | AEAD with AAD (tenant, object, key version), so tampering fails the auth tag. |
| Tampering | Forged policy bundle | The hybrid Ed25519 + ML-DSA-65 signature is verified before activation. |
| Repudiation | Admin denies an action | Every privileged operation is audited with its principal and requestId. Two-person approvals are recorded. |
| Info disclosure | Plaintext leaks through logs | pino redaction paths. Plaintext is never logged. Decrypt returns data only to the authorised principal. |
| Info disclosure | Enumeration across tenants | 404 for foreign ids and uniform timing on auth failures. |
| DoS | Request floods | Caddy edge limits, per-tenant Redis token buckets and quotas. Excess requests get 429 problem+json. |
| DoS | Queue poisoning | Bounded attempts, a DLQ, and zod validation of payloads. |
| Elevation | Agent escalates its scope | Each operation's capability is checked against the grant scope and policy. Deny by default. |
| Elevation | AI proposal approves itself | Approver ≠ proposer is enforced in both the DB and the service. The APEX service principal has no approve permission. |

## Re-entry R-2 — Quantum Readiness and plan tiers (requested 2026-11-10)

**Source.** User decisions on 2026-11-10: build "Readiness + tiers", with the scanner on the customer side. The
discussion before it ranked PQC products by the data they hold. A product that keeps only crypto *metadata* avoids
the root-key, breach, residency and liability risks of hosting customer keys and plaintext.

**New requirements.**

1. **Readiness deployment mode.** One build that can run as the full trust plane (`platform`, today's behavior) or
   as a metadata-only quantum-readiness service (`readiness`). In `readiness` mode, customer key material and
   plaintext never enter the system: VAULT, customer key lifecycle and agent grants are switched off. Evidence,
   approvals, APEX, team, billing and the tenant signing key (bundles and checkpoints) stay.
2. **Customer-side scanner.** A CLI that runs inside the customer's network and discovers cryptography in use:
   - TLS endpoints: negotiated protocol, cipher and key-exchange group, plus the leaf certificate;
   - certificate files: public-key algorithm and size, signature algorithm, expiry;
   - dependency manifests: known crypto libraries and their versions.

   It uploads findings only. It never reads private-key files and never sends key material, plaintext or file
   contents. A dry-run prints the exact payload so the customer can review it before anything leaves their
   network.
3. **Metadata-only ingest.** A tenant-scoped endpoint, authenticated by a revocable scanner credential, that
   accepts the findings and refuses anything that looks like secret material.
4. **Crypto inventory and risk.** Findings become crypto assets with a deterministic 0–100 quantum-risk score, and
   the inventory exports as a CycloneDX 1.6 CBOM.
5. **Migration over external assets.** Migration plans can cover scanned assets. A plan is validated when a later
   scan shows its assets on a PQC or hybrid algorithm, or no longer present. Validation comes from scan evidence,
   not a checkbox.
6. **Plan tiers.** Free (no subscription), Team and Enterprise. Limits and features are defined in one place in
   code and enforced on the API with a stable `PLAN_LIMIT` error. The console shows usage and an upgrade path.

**Research findings.**

- **Standards.** NIST FIPS 203 (ML-KEM), 204 (ML-DSA) and 205 (SLH-DSA) are final (August 2024). NIST IR 8547
  (draft, November 2024) deprecates quantum-vulnerable public-key algorithms (RSA, ECDSA, EdDSA, DH, ECDH) after
  2030 and disallows them after 2035. CNSA 2.0 sets earlier national-security dates. The US federal inventory
  mandate (OMB M-23-02) makes a crypto inventory the first deliverable. These anchor the risk-score weights and the
  2030 and 2035 horizons.
- **Inventory format.** CycloneDX 1.6 (April 2024) added the Cryptography Bill of Materials (CBOM): components of
  type `cryptographic-asset` with `cryptoProperties` (`assetType` algorithm, certificate or protocol;
  `algorithmProperties`, `certificateProperties`, `protocolProperties`). Exporting CBOM makes the inventory
  portable to other tools.
- **Discovery feasibility on Node 24.**
  - `node:tls` `getProtocol()`, `getCipher()` and `getEphemeralKeyInfo()` report the negotiated parameters, and
    `getPeerX509Certificate()` returns a certificate with `publicKey.asymmetricKeyType` and
    `asymmetricKeyDetails`.
  - `crypto.X509Certificate` parses PEM and DER certificate files without a native dependency.
  - Hybrid groups such as X25519MLKEM768 negotiate with OpenSSL 3.5. The scanner offers them and records what the
    server picks.
  - Discovering cloud KMS settings needs provider SDKs and credentials, so it is deferred to a later re-entry.
- **Risk.** "Harvest now, decrypt later" makes key exchange on long-lived traffic, and certificates valid past
  2030, the highest priority. Symmetric algorithms at 256 bits and SHA-2/SHA-3 at 256 bits or more are treated as
  quantum-adequate. AES-128 and SHA-1 are flagged as weak for other reasons.

**Constraints carried.** Same stack, the same invariants and gates, and no certification claims. The scanner is a
standalone workspace with no dependency on `@cz/core`, so it can ship to customers on its own.

**Go/No-Go (re-entry): GO.** No blocking unknowns. Cloud KMS discovery and a hosted external TLS check are
deferred.

## Re-entry R-3 — Clientless external discovery (requested 2026-11-11)

**Source.** User request on 2026-11-11: "how can we make this clientless?", then "yes, draft the R-3 re-entry",
starting with the domain-verification and external-scan slice. R-2 deferred "a hosted external TLS check"
(re-entry R-2 Go/No-Go), and this re-entry picks it up.

**Problem.** In R-2 every scanned asset needs `cz-scan` running inside the customer's network. For the
internet-facing part of an estate (public TLS endpoints and their certificates) that install step is avoidable: the
platform can find and probe those hosts itself, once the customer proves they own the domain.

**New requirements.**

1. **Monitored domains.** A tenant adds a domain (for example `customer.com`) and proves control by publishing a DNS
   TXT record. Only a verified domain is ever probed. Verification is re-checked daily, and a domain whose record
   disappears lapses and stops being probed.
2. **Host discovery without a client.** The hosts under a verified domain come from:
   - the apex and `www`;
   - Certificate Transparency (CT) logs, which list every publicly trusted certificate issued for the domain and
     its subdomains;
   - hostnames the customer adds by hand (CT misses hosts that only use a wildcard certificate).
3. **Platform-side TLS probing.** The platform probes each public host on the allowed ports and records the same
   metadata `cz-scan --tls` records: protocol, key-exchange group and leaf certificate. It does a TLS handshake
   only and sends no application data.
4. **Same inventory.** External findings join the existing crypto inventory as scanned assets with the R-2 risk
   score. They count toward exposure, export in the CBOM, and can be covered by migration plans that a later
   external scan validates. A host found both ways (by `cz-scan` and externally) is one asset.
5. **No new reach into the platform.** Probing outbound must not give an attacker a path to internal services
   (SSRF). A name that resolves to a private, loopback, link-local or otherwise non-public address is never
   probed. It is reported as "private: scan it with cz-scan".
6. **Plan tiers.** The number of monitored domains is a plan limit.

**Research findings.**

- **Domain control validation.** A DNS TXT record under an underscore label is the established pattern
  (CA/Browser Forum Baseline Requirements §3.2.2.4.7 "DNS Change"; Google Search Console, Microsoft 365 and
  others). Underscore labels never collide with real hostnames (RFC 8552). Re-validating periodically handles
  domains that change hands.
- **Certificate Transparency.** RFC 6962 / RFC 9162 logs are append-only and public. Chrome and Apple require CT
  for publicly trusted TLS certificates, so CT coverage of public hosts is close to complete. Reading raw logs needs
  a log monitor, which is too heavy for this re-entry. Search front-ends (crt.sh and commercial CT search APIs) answer
  "certificates for `%.domain`" in one HTTP call. crt.sh is free but rate-limits and is sometimes unavailable, so
  CT is a best-effort source behind an interface, with a fixture source for tests. Domain names sent to a CT search
  service are already public in CT, but the query reveals that the tenant is interested in them. SPEC §8 documents
  this, and the source can be disabled.
- **SSRF.** Outbound probing from a hosted service is a classic SSRF surface (OWASP SSRF Prevention Cheat Sheet;
  CWE-918). The known bypasses are DNS rebinding (a name that resolves to a public address at check time and a
  private one at connect time), mixed A/AAAA records, IPv4-mapped and NAT64/6to4-embedded IPv6, decimal or octal IP
  forms, and redirects. The standard mitigations, all used here:
  - resolve once;
  - refuse the host if *any* resolved address is non-public (IANA IPv4 and IPv6 special-purpose address
    registries);
  - connect to that exact address with SNI set to the hostname;
  - never follow redirects (TLS handshake only);
  - isolate the prober at the network layer, so a guard bug cannot reach the internal network.

  `node:net` `BlockList` implements the address check with no dependency.
- **Current topology.** In `compose.yaml` the worker is on the default network with Postgres, Redis, trust-core and
  the API, and it holds the database URL and its mTLS key. Probing from the worker would put an SSRF bug one hop from
  all of them. A separate prober container, with internet egress and no route to those services, holds no secrets
  worth taking (ADR-089).
- **Public-suffix check.** Refusing `com`, `co.uk` or `github.io` as a "domain" needs the Public Suffix List.
  `tldts` is the maintained, zero-dependency option. Pin the version at build time and verify it per ARCHITECTURE
  §8.
- **Ports.** Only ports that negotiate TLS immediately on connect are probed: 443, 8443, 465, 993, 995, 636, 853 and
  5061. STARTTLS (25, 587, 143, 110) needs a protocol dialog and is deferred.

**Out of this re-entry (later re-entries).**
- **R-4:** a GitHub/GitLab app that reads dependency manifests through the provider API (OAuth, push webhooks).
- **R-5:** read-only cloud connectors (AWS ACM/KMS/ELB, Azure Key Vault, GCP Certificate Manager/KMS).
- STARTTLS probing, raw CT log monitoring, and continuous (sub-daily) monitoring.

**Constraints carried.** Same stack, invariants and gates, and no certification claims. It works in both
`PRODUCT_MODE`s and never touches trust-core or key material. `cz-scan` stays the path for internal endpoints and
files.

**Product decisions (user, 2026-11-11: "go with your recommendations").**
1. Domain limits: Free 1, Team 10, Enterprise unlimited.
2. Every plan, Free included, gets the daily scheduled scan, plus at most one on-demand scan per domain per hour.
3. CT source: crt.sh by default (free, best-effort) behind the `CT_SEARCH_URL` interface. A production deployment
   can point it at a paid CT search API without a code change.
4. The prober's egress IPs are published for production deployments (README and QUICKSTART name where to find
   them), so customers can recognise or allowlist the probes.

**Go/No-Go (re-entry): GO.** No technical unknowns block it, and the product decisions are made.
