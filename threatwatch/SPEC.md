# SPEC.md — ThreatWatch

> Stage 2 behavioral contract · build_depth **standard** · sources: RESEARCH.md, ARCHITECTURE.md, DECISIONS.md ADR-001…015.
> Canonical numbering §1–§10. A section that does not apply says `N/A — <reason>`.

## 1. Overview & scope

**Problem.** SOC teams run many disconnected security products, so the analyst ends up doing correlation by hand. **ThreatWatch** is a multi-tenant security intelligence platform. It ingests signed telemetry from existing security products and turns it into evidence-backed alerts on a live operating picture, through this pipeline: normalize → enrich (geo, threat intel, asset) → correlate → detect → alert → notify. The core analyst path is **Dashboard → Alert → Source → Target → Related Events → Threat Intelligence → Timeline → Resolution**, and it never leaves the product.

**Personas → roles** (one organization per user in v1):

| Role | Persona | Summary of rights (full matrix in §4.2) |
|---|---|---|
| `owner` | Security Manager / org creator | everything; org settings; team incl. admins; manual job trigger |
| `admin` | Security Engineer | integrations, rules, intel, notification policies, delivery endpoints, reports, team (non-owner) |
| `analyst` | SOC Analyst / Incident Responder | triage + investigate alerts, search, assets metadata, read rules/integrations |
| `viewer` | Executive / Compliance / IT stakeholder | read-only dashboard, map, alerts, sources, assets, reports |

**Non-Goals (ADR-005, RESEARCH §6):**
- endpoint agent
- SOAR / automated response actions
- billing or payment UI (`has_payments` Deferred, ADR-006)
- SSO/SAML
- PDF export (reports are in-app snapshots + emailed summary)
- mobile app
- third-party map tiles
- live external threat-feed sync (ADR-013)
- multi-org membership

**Deferred metrics:** 99.9% ingestion availability and horizontal scaling are not measured on a single-host deploy (R12).

**Glossary:**

| Term | Meaning |
|---|---|
| Integration | a configured security product that pushes events |
| Batch | one signed ingest request |
| Event | one normalized record |
| Indicator | IOC: ip, domain, url, hash, email |
| Source | the threat-source entity (src IP / domain / indicator value) |
| Asset | a targeted host/IP/user in the org |
| Correlation group | connected activity sharing an entity within a window |
| Rule | a detection rule; immutable versions |

## 2. Data model

PostgreSQL 17 via Prisma 7:
- All ids are UUID v7 strings, generated by the app.
- All times are `TIMESTAMPTZ` in UTC.
- **Tenant** tables carry `org_id UUID NOT NULL REFERENCES organizations ON DELETE CASCADE`, plus an index led by `org_id`.
- **Global** tables are read-only reference data.
- Enumerations are `TEXT` + `CHECK`. No floating-point columns anywhere (INV-8).

**State machines** (`server/src/domain/states.ts`):

| Machine | Transitions |
|---|---|
| Alert | `new → acknowledged \| investigating \| resolved \| false_positive`; `acknowledged → investigating \| resolved \| false_positive`; `investigating → resolved \| false_positive`; `resolved → investigating` (reopen); `false_positive → investigating` (reopen). Escalation is orthogonal (`escalated_at`, `escalation_level`). |
| Email | `pending → sent \| failed`; `failed → pending` (backoff) `\| dlq`; `dlq → pending` (manual retry) |
| Delivery | `pending → delivered \| failed`; `failed → pending \| dlq`; `dlq → pending` (manual retry) |
| Batch | `pending → processing → done \| failed`; `failed → pending` (retry) |
| Integration status | `pending → active` (first verified event) `→ disabled → active` |
| Integration health | `unknown → healthy \| degraded \| silent` (ingestion-health job) |

## 3. API surface

- Base path `/api/v1`, JSON only.
- Session cookie auth (`__Host-tw_session`) unless noted.
- Mutations require `Origin` ∈ `APP_ORIGINS`.

**NativeEvent** (accepted per integration kind; `domain/normalize.ts` maps aliases):
- Required: `id` (string ≤200, becomes `source_event_id`) and `time` (ISO-8601; may be up to 24 h in the future, which is rejected with `TIME_SKEW`, and up to 30 d in the past).
- Optional: `category`, `action`, `outcome`, `severity` (0–10), `src_ip`/`src`/`source.ip`, `src_port`, `dst_ip`/`dst`/`destination.ip`, `dst_port`, `protocol`, `user`/`user_name`/`actor.user.name`, `hostname`/`host`/`device.hostname`, `domain`/`query`, `url`, `hash`/`file.sha256`, `process`, `message`.
- Kind-specific defaults:
  - firewall → `category: network`
  - edr → `process`
  - identity → `auth`

### 4.3 Domain-signal checklists (each item traceable to COMPLIANCE.md)

**`has_webhooks` (inbound ingest)**
- WH-1 **Signature first, DB second.** Before verification, the only read is `integrations.secret_enc` by primary key. No other row is read or written until `verifyIngestSignature` passes (INV-16).
- WH-2 **Idempotency.** `webhook-id` → `webhook_receipts` UNIQUE `(integration_id, message_id)` (INV-12). A replay returns 200 `{duplicate:true}` with no side effect. Per-event dedupe uses UNIQUE `(integration_id, source_event_id)` (INV-20).
- WH-3 **Retention ≥ the retry window.** Senders retry for up to 72 h, so receipts are retained **7 days** (retention-sweep).
- WH-4 **Anomaly flag.** If a batch was accepted but detection failed after 5 attempts (business state diverged), `ingest_batches.anomaly = true` and `detection_status = 'failed'`. It shows on the integration detail page as a retryable failed batch and counts toward `degraded` health.

**`has_geo`**
- GEO-1 Coordinates are `NUMERIC(9,6)` with CHECK `-90..90` / `-180..180` in `geo_ip_ranges` and `events`. The zod refine applies to any coordinate input.
- GEO-2 Map provider proxy: **N/A**. There is no external map provider; the map is a local SVG (ADR-010). `GET /api/v1/dashboard/geo` remains under the global rate limit.
- GEO-3 PII: coordinates are city centroids of attacker IPs, never precise locations of org assets. No asset location is stored.

**`has_websocket`**
- WS-1 Origin header checked against `APP_ORIGINS` in the HTTP `upgrade` handler before `handleUpgrade` (INV-17). A mismatch → `403` and the socket is destroyed.
- WS-2 Per-connection budget: the server pushes only. Inbound frames are limited to `ping` / `subscribe` with ≤20 messages per 10 s; beyond that → close 1008. Max frame size is 4 KB.
- WS-3 Channel authorization: the session is resolved from the cookie at upgrade, and the socket joins only `org:<session.orgId>`. Payloads carry `{kind, id}` only; the client refetches through scoped REST. Sockets are closed when their session is revoked (checked every 60 s).

**`has_scheduled_work`** (triggers T1–T7 per ARCHITECTURE §2.4)
- SW-1 **Effect assertions.** `server/test/jobs/<job>.test.ts` asserts the business effect for each trigger, and was written before the logic exists:
  - T1 a pending batch with a matching event yields an alert row
  - T2 a pending email becomes `sent` (transport fake records the message)
  - T3 a pending delivery becomes `delivered` (local receiver got the signed POST)
  - T4 an unacknowledged alert past its threshold gets `escalated_at` and an escalation email queued
  - T5 a silent integration becomes `silent`; ≥20 % rejects becomes `degraded`
  - T6 old events are deleted and the alert evidence snapshot remains
  - T7 a due schedule creates a `reports` row and report emails
- SW-2 **Every trigger is exercised.** There are seven triggers and seven effect tests. The dispatcher `JOBS` map is exhaustive, which the type system enforces via `satisfies Record<JobName, …>`.
- SW-3 **Per-tenant entry point.** Each job exposes `runXForOrg(scope, now)` alongside the `runX(now)` sweep. Tests use the per-org form.
- SW-4 **Idempotent claim.** Each job claims work with a conditional write:
  - batches: `UPDATE … SET claimed_at=$now WHERE id=$1 AND claimed_at IS NULL`
  - outboxes: `FOR UPDATE SKIP LOCKED` plus a status check
  - escalation: `UPDATE alerts SET escalated_at=$now WHERE id=$1 AND escalated_at IS NULL`
  - reports: `UPDATE report_schedules SET next_run_at=… WHERE id=$1 AND next_run_at=$due`

  Tests run each job twice and assert exactly one effect.
- SW-5 **Injected time.** `now: Date` is a parameter everywhere; workflows pass workflow time. Schedules are evaluated in **UTC**. Report `hour_utc` is UTC, and the UI displays it in UTC with the local equivalent.
- SW-6 **Observable outcome.** Every run writes `job_runs(processed, skipped, failed, error_text)`. Admin › Jobs shows the last run of each job with its counts and failed status, highlighted in red when `failed > 0`.
- SW-7 **Startup/shutdown.** `catchupWindow 10 m`, overlap `SKIP`. On start, only the most recent missed run within 10 minutes executes. SIGTERM stops polling, in-flight activities get 10 s, and Temporal retries anything unfinished.
- SW-8 **Smoke.** The smoke test forces `detection-sweep` and `email-drain` through `POST /api/v1/admin/jobs/:job/run` (owner, `JOB_TRIGGER_ENABLED=true` in the local deploy only) and asserts the effects: an alert exists, and the Mailpit API shows the email.

**`has_dual_write`** (DB → Temporal): **outbox pattern.** The `ingest_batches` row commits in the same transaction as its events, with `detection_status='pending'`. After commit, the api starts workflow `detect-<batchId>`, whose id is idempotent. `detection-sweep` (T1) reconciles any batch still `pending` after 30 s. The claim is `UPDATE … WHERE claimed_at IS NULL`. Retries: 5 attempts, then `failed` plus `anomaly`.

**`has_email`**
- EM-1 `pending_emails` has all checklist columns, plus `org_id`, `business_ref`, `next_attempt_at` and `claimed_at`; index `(status, next_attempt_at)`.
- EM-2 Rows are inserted in the triggering transaction: the alert's creation, the escalation, a report generation, or a user creation with a temporary password (only when `EMAIL_TEMP_PASSWORDS=true`; otherwise the password is shown once in the UI).
- EM-3 The drain (`email-drain`, T2) selects `pending` rows with `next_attempt_at ≤ now` (LIMIT 50, SKIP LOCKED) and sends via `services/email/transport.ts` (nodemailer SMTP). It then sets `sent` + `sent_at`, or `failed` + `error_text` + `attempts++`.
- EM-4 Backoff: 1 m, 10 m, 1 h. After 3 attempts the row goes to `dlq` and a structured `email.dlq` log line is written. Rows can be retried manually from Notifications › Log.
- EM-5 No synchronous sends. `sendMail(` is allowed only in the transport (INV-14), and only the drain calls the transport.
- EM-6 UNIQUE `(to_address, template_key, business_ref)` (INV-23). Re-firing the same trigger does not duplicate the email.

**`has_webhook_send`** (outbound deliveries)
- WS-OUT-1 `pending_deliveries` has all checklist columns (ADR-011 naming) and index `(status, next_retry_at)`.
- WS-OUT-2 The signature is computed at INSERT: Standard Webhooks `v1,base64(HMAC-SHA256(secret, id.signed_at.payload))`, stored and re-sent verbatim on every retry.
- WS-OUT-3 Each send carries `Idempotency-Key: <pending_deliveries.id>` and `webhook-id`/`webhook-timestamp`/`webhook-signature` headers.
- WS-OUT-4 Backoff: 1 m, 5 m, 30 m, 2 h, 6 h. After the 6th failed attempt (the initial send plus five retries) the row goes to `dlq` and a structured `delivery.dlq` log line is written.
- WS-OUT-5 The drain (`delivery-drain`, T3) selects `pending` and `failed` rows with `next_retry_at ≤ now` (SKIP LOCKED), calls `assertSafeUrl` and then POSTs to the validated IP (DNS pinned to the `assertSafeUrl` result, redirects not followed — ADR-028) with a 5 s timeout. A disabled endpoint's rows are not claimed until it is re-enabled. A 2xx response sets `delivered`; anything else sets `failed`/backoff.
- WS-OUT-6 Receiver guidance (documented in QUICKSTART): verify the signature, then persist `(webhook-id)` UNIQUE for at-most-once effect.

**`has_payments`: N/A in v1** (ADR-006). No monetary amounts are stored and no charges exist. Items 1–5 are not applicable. INV-8 forbids floating-point columns, so any future billing feature inherits the money rule.

### 4.4 Compliance baseline

`security_baseline` is blank, so the floor is **OWASP Top 10** with no regulatory regime. The password-verifier items are nonetheless applied as best practice (Gap 6), not as a compliance claim:
- PW-1 Offline breached-password screening against a bundled top-10k list, on register, password change and temporary-password reset → 400 `PASSWORD_BREACHED`.
- PW-2 Length 12–128 with no composition rules and no truncation.
- PW-3 The login limiter runs before the argon2 verify.
- PW-4 No periodic rotation and no security questions. Recovery: an owner/admin issues a temporary password (`must_change_password`), and an email reset is out of scope for v1.

At-rest encryption: the column-level AES-256-GCM in S8 covers integration and delivery secrets. Volume encryption is delegated to the deploy target, so it is ⚠ (delegated) in COMPLIANCE.md.

  - Replaying the same `webhook-id` → `duplicate:true`.
  - p95 ingest of a 500-event batch < 1 s.

**F-4 Detection rules, Temporal engine & correlation**
- Rule DSL:
  - Shape: `{match:{all|any:[{field, op, value}]}, threshold?:{count 2..10000, windowSec 60..86400, groupBy field}}`.
  - Fields: `category, action, outcome, severity_in, src_ip, dst_ip, dst_port, user_name, hostname, domain, url, file_hash, process_name, src_country, indicator_match`.
  - Ops: `eq, neq, in, contains, starts_with, cidr, gte, lte, exists`.
- Rule features: versions (immutable), dry-run test, enable/disable, stats (alerts/day, FP rate = false_positive ÷ closed, MTTA, MTTR).
- `detectBatch` workflow plus `detection-sweep`. Correlation: same org + shared entity (src_ip, asset, indicator, user) within 30 min of event time joins the group.
- Risk score: `round(severityWeight × confidence/100 × criticalityMultiplier)`, capped at 100. Severity weights: critical 100, high 75, medium 50, low 25, info 10. Criticality multipliers: critical 1.0, high 0.9, medium 0.75, low 0.6, none 0.75.
- Suppression: the same rule + group key within `suppression_min` extends the open alert (adds evidence) instead of creating a new one.
- Eight seeded default rules per org:
  - brute force: ≥10 auth failures from one src in 5 min
  - known-malicious IP (indicator_match)
  - malware hash match
  - suspicious DNS to an indicator domain
  - port scan: ≥20 distinct dst_port… expressed as ≥30 network events from a src in 2 min
  - impossible-country admin login (category auth, outcome success, user contains `admin`, src_country not in `allowedCountries` value list)
  - EDR high-severity process (severity_in ≥ 8)
  - cloud console failure burst
- *Accept:*
  - Ingest 12 failed logins from one IP → a brute-force alert within 30 s, with 12 evidence events and an MITRE T1110 link.
  - A second burst within 30 min extends the same correlation group.

### 5.2 Key Workflows (1:1 with RESEARCH.md Step 3)

### W1 Security Telemetry Ingestion — Enterprise Source → ThreatWatch
- W1.1 An admin connects a source: Integrations › Add integration (name, kind) → `POST /api/v1/integrations`.
- W1.2 Authenticate and validate the connection: the secret is shown once with the ingest URL and a signing snippet; "Send test event" → `POST /api/v1/integrations/:id/test` → status `active` when accepted.
- W1.3 Receive security events: the source posts signed batches to `POST /api/v1/ingest/:integrationId`.
- W1.4 Validate incoming data: signature first; zod schema per event; rejected events are recorded in `ingest_errors` with code + index.
- W1.5 Normalize each event into the ThreatWatch event model (`domain/normalize.ts`).
- W1.6 Enrich with context: geo (`geo_ip_ranges`), intel (`indicators`), and the asset (match or auto-create).
- W1.7 Store events: dedupe on `(integration_id, source_event_id)`; the batch outbox row is written in the same transaction.
- W1.8 **Terminal:** report ingestion health and errors on the Integration detail page (counters, events/hour, errors table, batches, health badge).

### W2 Threat Detection — Event → Detection → Alert
- W2.1 Receive normalized events: `detectBatch` (or `detection-sweep`) claims the batch.
- W2.2 Evaluate detection rules: the current version of each enabled rule, match + threshold in event time.
- W2.3 Correlate with related activity: join or create a correlation group by shared entity within 30 min.
- W2.4 Enrich with threat intelligence: indicator matches attached to the alert.
- W2.5 Determine severity and confidence: from the rule version, giving the risk score with asset criticality.
- W2.6 Generate the alert when criteria are met (≥ `required_evidence` events, outside suppression), with evidence rows.
- W2.7 **Terminal:** notify the appropriate users. Matching policies enqueue email and delivery in the same transaction, and a live `alert.created` push reaches the dashboard and alert list.

### W3 Real-Time Monitoring — Events → Security Operations Dashboard

## 7. Error contract

Every non-2xx response is `application/problem+json`:

```json
{ "type": "https://threatwatch.local/errors/validation", "title": "Validation failed", "status": 400,
  "detail": "2 fields failed validation", "instance": "/api/v1/rules",
  "code": "VALIDATION_FAILED", "requestId": "01J…",
  "errors": [ { "field": "name", "message": "Name must be at least 3 characters", "code": "TOO_SHORT" } ] }
```

**Error codes by status:**

| Status | `code` values |
|---|---|
| 400 | `VALIDATION_FAILED`, `PASSWORD_BREACHED`, `PASSWORD_TOO_SHORT`, `UNSAFE_URL`, `TIME_SKEW`, `PAYLOAD_TOO_LARGE_EVENTS`, `LIMIT_REACHED`, `SELF_RESET` (a malformed list cursor is `VALIDATION_FAILED` with `errors[{field:'cursor', code:'INVALID_CURSOR'}]`) |
| 401 | `UNAUTHENTICATED`, `INVALID_CREDENTIALS`, `INGEST_UNAUTHORIZED` |
| 403 | `FORBIDDEN`, `CSRF_ORIGIN`, `ORIGIN_NOT_ALLOWED` |
| 404 | `NOT_FOUND` (includes every cross-tenant id) |
| 409 | `CONFLICT`, `EMAIL_TAKEN`, `INVALID_TRANSITION`, `IDEMPOTENCY_CONFLICT`, `LAST_OWNER`, `VERSION_CONFLICT`, `INDICATOR_EXISTS`, `ALERT_CLOSED`, `NOT_RETRYABLE`, `ENDPOINT_IN_USE` |
| 413 | `PAYLOAD_TOO_LARGE` |
| 415 | `UNSUPPORTED_MEDIA_TYPE` |
| 428 | `PASSWORD_CHANGE_REQUIRED` (also the WebSocket upgrade answer for such a session) |
| 429 | `RATE_LIMITED` (with a `Retry-After` header) |
| 500 | `INTERNAL_ERROR` (generic detail, never a stack) |
| 503 | `DEPENDENCY_UNAVAILABLE` (e.g. the job trigger when Temporal is down) |

- `requestId` echoes the `X-Request-Id` request header (Caddy forwards or mints one) and is returned on every response header.
- Per-event ingest rejections are reported inside the 202 body (`errors[{index, code, message}]`), not as a non-2xx.
- The web client (`web/src/lib/api.ts`) parses the problem body and maps `errors[]` onto form fields; `code` drives the UI copy.
